# 活动报名无人值守与 SKU 备用槽实施计划（2026-08-30）

## 已确认的长期规则

1. 每场活动仍向平台提交全部 ERP 在售商品。历史无动销登记不再提前排除；平台本场明确返回
   无动销后，仅在本场归类，不报警、不阻断其他商品，下场仍重新尝试。
2. 普通 SKU 的价格资格差额不超过 2.00 元时自动处理：
   - 最低标价线冲突：报名价最多比 ERP 日常价低 2.00 元；
   - 最低普惠券后价线冲突：优先增加单品立减，最多 2.00 元；
   - 两种处理均允许最终到手价最多比 ERP 目标价低 2.00 元，并写入逐 SKU 审计。
3. 显式定制 SKU 或显式定制专用链接可以自动降低价格，但叠加所有活动优惠后的最终买家价
   不得低于该逻辑 SKU 首次纳管时 ERP 日常价的 20%。首次纳管基准一经写入不得自动下调。
4. 普通 SKU 超过 2.00 元的冲突不靠继续降价解决，改用同一商品下的干净备用物理 SKU。
5. 试点商品固定为淘宝商品 `793202812082`、ERP 产品 `PPS24410040513`（樱桃木 2024 款
   新升降桌）。用户已精确授权：若该商品当前活动阻碍 SKU 编辑，可只撤出该商品，再新建备用
   SKU 做一次试点。授权不扩展到其他商品。

## 反面审查及结论

### 第一轮：价格规则是否自相矛盾

- 反对：2 元差额并不都是单品立减能解决；最低标价线要求直接降低报名价。
- 处理：把两条价格线分开处理。报名价和最终价的最大偏差分别审计，任一累计超过 2.00 元立即
  转备用 SKU，不允许连续叠加多次 2 元绕过上限。
- 反对：定制价降到原价 20% 后再叠加官方立减，实际到手可能低于 20%。
- 处理：20%定义为“所有优惠叠加后的最终买家价底线”，不是报名价底线。
- 反对：所谓“原价”可能被以后的人改低。
- 处理：新增不可自动降低的 `baseline_daily_price`，首次纳管时固化；只有人工在 ERP 提高基准，
  自动化不得下调。

### 第二轮：SKU 轮换会不会污染订单和库存

- 反对：旧轮换代码把已有淘宝 skuId 重新分给另一规格，旧订单会被新含义污染。
- 处理：旧的标签平移方式永久退役。新方案只新增物理备用槽，旧 skuId 永远保留原逻辑身份；
  所有映射带生效/失效时间，历史订单按下单时映射回 ERP SKU。
- 反对：复制库存会造成同一件库存被多个 SKU 重复出售。
- 处理：同一逻辑 SKU 同时只能有一个 `active` 槽；备用槽初始库存为 0，激活时通过一个原子步骤
  转移可售库存，失败则全部保持原状态。
- 反对：淘宝商家编码不能重复。
- 处理：物理槽使用唯一后缀编码，ERP 另存逻辑 SKU 编码；名称、材质、尺寸、图片、重量等业务
  属性必须与源 SKU 指纹一致。

### 第三轮：轮换是否真的能绕开历史价格线

- 反对：平台可能按商品而不是 skuId 计算历史价格，新增 SKU 也可能继续受限。
- 处理：升降桌试点必须先新建一个备用槽，再只读进入同一活动候选资格页验证两条价格线。
  如果新槽仍继承旧线，立即判定 `item_level_price_history`，停止扩大 SKU 池；不能以反复建 SKU
  试探平台。
- 反对：公开规则检索不到足以证明平台允许的官方说明。
- 处理：不把猜测写成能力。只有升降桌真实页面、官方导出和候选资格回读共同证明后才开放推广。

### 第四轮：活动中修改和撤出风险

- 反对：修改活动中的商品可能破坏现有报名、单品立减或正在成交的 SKU。
- 处理：试点前读取该商品的全部活动绑定、当前订单和商品导出。只撤出明确阻碍编辑的活动中的
  `793202812082`，不撤其他商品；旧 SKU 不删除。试点外的长期方案只在活动发现后的准备窗口
  补足备用槽，不在活动执行中临时撤出。
- 反对：撤出后平台编辑失败，商品会失去活动权益。
- 处理：先保存撤出前活动、SKU、价格、库存和属性 SHA256；只有编辑页已验证可新增且会话稳定才
  撤出。编辑失败停止，不盲目重试；恢复只能使用原精确活动和原 SKU 清单。

### 第五轮：无人值守是否会变成无限重试或无限建 SKU

- 反对：页面变化会导致程序持续建槽、持续撤出或反复提交。
- 处理：每个逻辑 SKU 每场最多一次槽切换；每个商品池有硬上限；平台写入前领取一次性数据库
  权；未知结果不重试。二维码/验证码只通知用户扫码，成功后从未写入步骤续接。
- 反对：每次报名都尝试无动销商品会积累永久排除。
- 处理：无动销结果只绑定本场 workflow，不进入下一场排除清单；下一场从全量在售集合重新开始。
- 反对：备用槽仍可能天天轮换。
- 处理：状态为 `clean -> reserved -> active -> cooling -> clean`。只在普通 SKU 差额超过 2 元且
  当前槽不合格时换槽。池容量由价保窗口与活动间隔计算，达到上限后等待最早槽冷却，不新增。

以上反对意见均已转化为可执行规则或硬停止条件；没有遗留的“靠程序猜测后继续写平台”路径。

## 完整实施计划

1. **政策与计算层**
   - 更新唯一活动政策：全量报名、2 元两线自动处理、定制最终价 20%底线、受控备用槽。
   - 价格计算输出原值、调整原因、调整额、最终偏差和证据时间；禁止累计绕过上限。
2. **数据层**
   - 新增逻辑 SKU 基准价、物理槽、映射历史、槽状态、价格线/冷却期和一次性变更尝试表。
   - 迁移时只导入现有映射，不猜备用槽；旧订单映射保持不变。
3. **ERP 编排层**
   - 每场从全部在售商品生成报名范围，不读取历史无动销作预排除。
   - 自动解决 2 元内冲突和定制价格；大额普通冲突进入槽选择。
   - 仅在活动发现、ERP 价格/SKU 变化、最终提交前和提交后刷新证据，不做每日全量抓取。
4. **Web-Agent 安全商品编辑层**
   - 新增精确 itemId 的商品编辑预览、创建备用槽、库存切换和导出回读能力。
   - 只允许 ERP 提供的完整属性指纹与唯一物理槽编码；禁止删除旧 SKU、改商品标题或碰其他商品。
5. **升降桌试点**
   - 只读确认 `793202812082` 的活动、订单、SKU、库存和页面可编辑性。
   - 必要时只撤出该商品；新增一个备用槽；导出核对所有原 SKU 未变、新槽属性一致、库存不重复。
   - 只读验证新槽是否获得独立价格资格线。用户检查一次页面后，才允许进入报名流水线。
6. **测试和发布**
   - 单元测试覆盖两种 2 元线、20%底线、全量无动销报名、槽状态机、历史订单映射、并发/中断/
     未知结果和池上限。
   - Web-Agent 使用静态页面和本地浏览器测试精确选择器；升降桌真实试点严格单次。
   - 通过后提交、推送、统一部署，核对迁移、版本、health/ready、运行源指纹和结构化审计。

## 完成标准

- 每场默认尝试全部 ERP 在售商品；无动销失败不影响其他商品且下场重新尝试。
- 小额差异和定制差异不再找用户，所有让利均在新边界内可审计。
- 普通大额差异仅使用经验证的干净备用槽，旧订单、库存和活动记录不串位。
- 同一批平台写入最多一次；二维码之外不需要用户逐商品处理。
- 升降桌试点必须证明“新物理 SKU 的价格资格确实独立”，否则不推广轮换方案。
