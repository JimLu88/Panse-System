# 畔色 ERP → 群晖 DS923+ 迁移完整方案 (Runbook)

> 2026-06-13 制定。本文是**可执行迁移总纲**;细节路径/安全清单见同目录 [群晖部署清单.md](群晖部署清单.md)。
> 原则:**财务零损伤**、可随时回滚、不暴露公网、机密不进镜像。

---

## 0. 硬件底数与总策略

| 项 | DS923+ 现实 | 影响 |
|---|---|---|
| CPU | AMD Ryzen R1600 双核四线程, 无 AVX-512, **无 GPU** | 渲染/抓取类不适合放它 |
| 内存 | 现配 **8GB** (最大 32GB) | 跑运行时三件套够用; 设好资源上限即可, 高峰持续吃紧再加到 16GB(见建议①) |
| 存储 | SATA HDD + 可选 NVMe 缓存 | 大文件(图库/归档)主场, DB 建议放 NVMe 卷或加读写缓存 |

**总策略:NAS 只跑"运行时"(db / api / 静态前端), 不跑"重活"(浏览器抓取 / 构建 / AI / 渲染高峰)。**

### 什么跑在哪(明确分工)
| 组件 | 位置 | 原因 |
|---|---|---|
| postgres / api / nginx(静态前端) | **NAS** | 常驻轻量, 7×24 |
| 图库 / 归档 / 导出 Excel / 下单图存档 | **NAS 共享文件夹** | 大文件主场 + Hyper Backup |
| Panse-Web-Agent(Playwright 抓淘宝/万师傅) | **留 PC** | Chromium 重 + 扫码要人 + Windows DPAPI |
| AI 识图 / OCR | **云 API(uniapi)** | NAS 无 GPU |
| 镜像构建 / tsc / 类型检查 | **PC** | 4GB NAS 编译会 OOM(512MB 容器都炸过) |
| 线框图生成器(方案C 子程序) | NAS 可跑(零重依赖, 仅 wkhtmltoimage), 但**作为独立子程序经接口对接**, 见 §7 |
| 模型缓存 / 浏览器内核 / build123d(方案A) | **PC / D 盘** | 太大, NAS 不放 |

## 阶段 0 — PC 侧打生产包 (我做, 0.5 天)

现有 `docker-compose.prod.yml` 已完成: 前端多阶段构建→nginx、api 2 workers+alembic、db 不暴露端口。**待补的差距项:**

- [ ] **资源上限**(按 8GB 配): `mem_limit`/`cpus` — db ≤2g、api ≤2.5g(2 workers)、nginx ≤256m(留 ~2.5-3g 给 DSM 自身);postgres `shared_buffers=384MB`、`max_connections=50`。
- [ ] **时区**: 所有容器加 `TZ=Asia/Shanghai` + 挂 `/etc/localtime:ro`。**关键** — 18:00 下单图、次日 10:00 作废检查、06:30 取数全靠它。
- [ ] **卷挂载补全**: prod compose 补 `storage`(归档/缩略图)、`gallery`(产品图库) 两个 bind 挂载到 NAS 共享文件夹(代码已抽 `GALLERY_ROOT` 环境变量, 零改动)。
- [ ] **Web-Agent 跨机**: api 服务加 `WEB_AGENT_URL=http://<PC局域网IP>:8500`;输出目录改 SMB/NFS 挂载(详见清单附1)。
- [ ] **机密外置**: 确认 `.env` 列全 `POSTGRES_PASSWORD / JWT_SECRET / ANTHROPIC_API_KEY / SETTINGS_ENCRYPTION_KEY / PUBLIC_HOST` — **不进镜像**。
- [ ] **镜像瘦身核查**: 保留 wkhtmltox + Noto CJK 字体(下单图/线框图要); **确认 opencv 未进镜像**(线框图方案C 零依赖, 不需要); 删测试依赖。
- [ ] PC 上 `docker compose -f docker-compose.prod.yml build` 跑通 + 本地起一次自测。

## 阶段 2 — 镜像 + 数据搬运 (我做 + 你配合传输, ~1-2 小时, 视图库大小)

- [ ] **镜像**: PC `docker save panse-system-api panse-system-web ... | gzip` → SMB 拷到 NAS → `docker load`。(或 NAS 上直接 build, 但 4GB 编译慢且可能 OOM, **优先 save/load**。)

## 2. 回滚方案 (任一阶段失败)

- 阶段 0-3 失败: NAS 侧 `docker compose down`, **PC 原系统从未停**, 零影响。
- 阶段 4 切换日失败: 立即把入口切回 PC(PC 数据是切换前最新), NAS 留作再调试。**切换前 PC 终量 dump 是回滚锚点。**
- 数据层: 每步 dump + btrfs 快照, 任何一步可回到上一致点。

## 3. 风险与缓解

| 风险 | 级别 | 缓解 |
|---|---|---|
| 8GB 内存高峰吃紧 | 中 | 设 `mem_limit`(db 2g / api 2.5g); postgres `shared_buffers` 调小; 持续吃紧再加到 16GB |
| R1600 渲染下单图慢/打满 CPU | 中 | 单并发队列限流(建议③); 维持"每批20张" |
| 机密迁移遗漏/仍用默认密钥 | 中 | 阶段2 强制设 `SETTINGS_ENCRYPTION_KEY` + 重录, 启动检查无警告 |
| 时区错 → 定时任务错点触发 | 中 | 阶段0 设 TZ; 阶段3 核对下次触发时间 |
| 图库传输窗口过长 | 低 | 先报体积定窗口; 可先拷存量, 切换日只增量同步 |
| Web-Agent 跨机连不上 | 低 | PC 防火墙放局域网 8500(不映射公网); Bearer token 已有 |

## 6. 针对 DS923+ 的 8 条建议

1. **内存按 8GB 用, 设好资源上限** — 8GB 养 DSM + postgres + api + nginx 够用, 关键是给每容器设 `mem_limit`(db 2g / api 2.5g)别让单容器吃满。日常监控内存, 高峰持续吃紧再加到 16GB(DS923+ 最大 32GB, 加装非必须)。
2. **Web-Agent 必须留 PC** — Chromium 抓取在 R1600 上又慢又重且扫码要人; 结果走现有 ingest API 推 NAS, 架构天然支持。
3. **渲染类任务单并发限流** — wkhtmltoimage(下单图/线框图) 是 CPU 大户, 加队列避免打满双核拖卡 DSM; 维持"每批 20 张"。
4. **构建永远在 PC** — 打镜像/tsc/类型检查不上 NAS;NAS 只 `docker load` 运行时镜像。
5. **大文件放 NAS 是主场** — 图库/导出/归档放共享文件夹 + Hyper Backup, 比 PC 的 D 盘更稳;"太大不方便"的是模型缓存/浏览器内核(已划给 PC)。
6. **每容器设资源上限** — `mem_limit`/`cpus` + postgres `shared_buffers≤256MB`, 防单容器拖垮整机。
7. **DB 卷尽量上 NVMe/SSD 缓存** — HDD 上 postgres 随机 IO 慢, 财务查询体感差; DS923+ 可加 NVMe 做读写缓存。
8. **安全三件套** — 不开公网端口 + DSM 防火墙只放内网/Tailscale 网段 + 正式加密密钥落地;这台 NAS 上是全部财务数据。

## 7. 线框图子程序(方案C)与本次迁移的关系

- 方案C 已验证可达设计师水准, 将作为**独立子程序**(不写死进 ERP, 仅接口对接)。
- 它零重依赖(纯 Python + wkhtmltoimage), NAS 上能跑;但按"独立子程序"定位, 建议**独立容器**, ERP 经 HTTP 接口调用(传产品结构配方 → 返 PNG/SVG)。
- 迁移时**不阻塞主系统**: 先迁 ERP 三件套, 线框子程序作为后续独立容器加挂即可。方案A(build123d 爆炸图)依旧独立、放 D 盘 AI 目录, 不上 NAS。
