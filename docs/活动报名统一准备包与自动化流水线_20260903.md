# 活动报名统一准备包与自动化流水线（2026-09-03）

> 历史方案，冲突流程已被用户 2026-09-04/05 的固定短流程替代。
> 当前执行入口为 [固定步骤与成果](campaign-signup-frozen-steps.md)。下文的证据刷新、
> 准备包时效和长链预检不得恢复为报名门槛；保留正文仅供追溯。

## 结论

活动报名改为“一条长期流水线”，不再为每次活动临时拼脚本。系统先把 ERP 商品、
SKU、日常价、目标价、官方力度、两条官方价格线、单品立减、动销提示和证据时间编译成
一份不可变准备包。准备包按商品给出 `ready`、`deferred_whole_item` 或
`excluded_by_explicit_policy`，并停在平台最终写入之前。

一个坏商品不会阻断其他安全商品；但活动身份错误、证据过期、已有未知写入、登录失效等
全局风险会阻断整份准备包。准备包最多有效 6 小时，过期后只能只读刷新再生成新版本。

```text
ERP 在售全集
  -> 只读官方证据
  -> 按商品完整核验（价格、SKU、范围、时效）
  -> 不可变准备包（逐商品决定 + 哈希 + 到期时间）
  -> [唯一尚未执行的最后一步]
  -> 一次性平台写入权 -> 上传/提交 -> 官方终态 -> 新鲜逐 SKU 回读
```

## 永久规则

1. 每场活动重新纳入全部 ERP 在售商品。历史无动销仅提示；本场平台明确判定无动销时安静
   结束该商品，不报警、不重试，下场再次纳入。
2. 真实 SKU 报名价必须精确等于 ERP 日常价。哪怕只差 0.01 元，也不自动改价；该商品
   整品暂缓，其他商品继续。
3. 程序不得为绕过历史价格线创建、平移或轮换物理 SKU。SKU 身份维护是独立商品维护动作，
   必须另有用户对精确商品的授权。
4. 只有 ERP 权威字段标记的定制/占位 SKU 可以使用安全低价；默认所有优惠后的最终价不得低于
   首次纳管日常价的 20%，基准只能人工提高，程序不能下调。用户对当前计划逐 SKU 明确批准
   固定活动价时，可通过 `custom_signup_price_authorized=淘宝SKUID:价格` 精确放行低于该比例的
   定制价；不得按商品名推断、不得扩展到其它 SKU，也不修改 ERP 日常价。
5. 定制专用链接、补差价链接或服务链接只能通过显式商品级标记或“全 SKU 均为权威占位”
   判定，禁止按商品名关键词误杀正常家具链接。
6. 任一商品的 SKU 不完整、价格证据缺失/过期、最终价算式不符或活动价线冲突，均整品暂缓；
   不允许只报其中几个 SKU。
7. 上传本身即可能产生平台写入。系统没有“上传试价”；写入前必须先领取数据库唯一写入权。
8. 已领取写入权后的超时、重启或未知结果只能回读或走精确事故恢复，不得自动再报。
9. 成功必须同时有平台终态和本次活动的新鲜逐 SKU 回读；按钮返回成功、文件生成或 HTTP 200
   都不单独代表报名成功。
10. 登录、二维码、验证码和平台风控是唯一需要用户介入的正常门；二维码必须发送到飞书，
    且不得保存账号凭据。

## 多轮反方审查

### 第一轮：每天全量保存证据是不是太重

- 反对：活动期间价格通常不变，每天抓全店浪费资源。
- 结论：不做永久每日全量抓取。活动发现后或报名窗口前只读刷新一次；准备包最长 6 小时，
  临近最终提交才刷新。长期活动只在新增/修正窗口刷新。

### 第二轮：历史无动销直接排除不是更快吗

- 反对：曾经无动销的商品可能后来有订单，永久排除会漏报。
- 结论：历史登记只作提示。每场重新尝试，平台本场失败后仅安静排除本场。

### 第三轮：差 2 元以内自动调一下不是更省事吗

- 反对：金额很小，似乎风险可接受。
- 结论：真实 SKU 的 0.01 元也可能改变价格承诺、价保和利润口径，并违反“报名价等于日常价”。
  小差额也整品暂缓；只有用户逐 SKU 明确写入计划的定制让利才可执行。

### 第四轮：价格线不合格时轮换 SKU 能提高成功率

- 反对：新 SKU 没历史价，报名更容易。
- 结论：轮换会污染库存、订单归因、售后、历史证据和平台规则判断，且会形成永无止境的维护。
  自动化禁止轮换。系统的目标是稳定识别可报范围，不是规避平台规则。

### 第五轮：一个商品有问题是否应整场停止

- 反对：整场停止最安全。
- 结论：把错误分为商品级和全局级。商品级整品隔离，其余商品继续；错活动、证据过期、未知
  写入等全局级错误整场停止。准备包同时核对报名行和单品立减行，防止只检查一半。

### 第六轮：准备包生成后 ERP 数据被改了怎么办

- 反对：旧准备包可能在新价格上提交。
- 结论：库存、映射、价格、政策、证据、活动身份和执行历史共同进入源哈希；包最多有效 6 小时。
  最终执行前必须重算并匹配哈希，不匹配或过期即失效。

### 第七轮：网络超时后自动再点一次更省人

- 反对：多数超时只是响应丢失。
- 结论：超时可能已写入，重试会重复报名。领取写入权后永不自动重试，只允许官方回读；写入权
  领取前的只读步骤可以重做。

### 第八轮：平台按钮或页面结构变化怎么办

- 反对：页面自动化迟早漂移。
- 结论：Web-Agent 必须锁活动标题、双 ID、signRecordId、阶段、档期和力度；选择器只能在目标
  容器内找语义明确的只读/提交控件。多个候选、遮罩、跳页或身份不一致均停，不盲点、不强点。

### 第九轮：已报名、暂停、处理中如何判断

- 反对：平台状态文案不统一，可能误报失败。
- 结论：平台终态与活动类型分开解释；未来长期超级立减的“暂停”可表示待生效，但仍需价格逐
  SKU 相同。处理中只能等待/回读，不能重新提交。

### 第十轮：准备程序的机器钥匙会不会误调用报名接口

- 反对：历史活动服务身份权限较宽。
- 结论：准备包使用独立加密机器身份，只能访问 `/api/campaigns/prepare-final-bundle`；旧活动
  身份不能调用该入口，新身份也不能调用 prepare、refresh、恢复、报名或改价接口。

### 第十一轮：03 正在报名时部署会不会中断现场

- 反对：重启 ERP/Web-Agent 可能把在途平台动作变成未知结果。
- 结论：发布前必须确认 03 到达安全断点且 Web-Agent 无在途作业。存在已领取写入权或活动作业时
  不部署；只记录等待，不把“进程不见了”当作未写入。

### 第十二轮：日志太多会不会继续把人淹没

- 反对：每个暂缓商品都报警，用户仍需天天处理。
- 结论：无动销静默；商品级暂缓进入一次汇总；只有需要登录或全局门失败才即时通知。相同
  `workflow_key + source_sha256` 复用同一准备包，不重复提醒。

### 第十三轮：迁移或发布失败怎么办

- 反对：新增表会影响现有报名。
- 结论：新表是旁路追加，不修改历史执行表；迁移可回滚。发布必须同时核对 migration head、
  API/Web 同一版本、health/ready、四容器和运行源指纹，任一不一致不交付。

经过上述审查，已没有未处理的程序级反方意见。仍不可消除的是淘宝登录/验证码、平台规则改变、
平台不可用及官方不提供候选价格证据；这些被定义为明确外部门，而不是由程序猜测或绕过。

## 正式入口与边界

Windows/NAS 正式脚本：

```powershell
.\scripts\campaign_prepare_final_bundle_nas.ps1 `
  -WorkflowKey '<固定 workflow_key>' `
  -PlanId <固定计划ID> `
  -Mode refresh_and_compile
```

三种模式：

- `compile`：只使用 ERP 已有数据和证据生成准备包。
- `refresh_and_compile`：先执行既有只读证据刷新，再生成准备包。
- `read_latest`：只读最近准备包。

固定边界：`platform_write=false`、`account_action=false`、`price_change=false`、
`sku_rotation=false`、`notification=false`、`automatic_retry=false`、
`write_claim_created=false`。

## 03 接续规则

03 只接收 `ready_for_final_submission=true` 且未过期的准备包。它必须先比较 plan、workflow、
活动身份、policy/source/manifest 哈希及数据库写入权；只有全部一致，才进入既有“一次写入 +
平台终态 + 新鲜逐 SKU 回读”流程。当前 03 的在途计划仍按其已有精确 V6 恢复边界收口，不得被
通用准备包自动重跑；待其到达安全断点后，再把现场事实编译为新准备包接入统一流水线。
