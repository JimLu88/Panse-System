# 活动联报机制 · 设计稿（2026-07-16，待用户拍板）

> 用户诉求（3件）：①一次联报多活动 ②自动查后台报名时间→档期日历自动更新 ③到期飞书提醒运营（不依赖 AI 在场）。
> 本稿定方向，拍板后再动工。关联：`activity_calendar_service` / `activity_upload_service` / `web_agent_service` / `notify_service` / 前端 `ActivityAutoFillTab.tsx`。

## ★拍板结论（2026-07-16）
用户定：**重心 = D（ERP 主动多推）**——不靠千牛联报计划提交，ERP 自己 WA 驱动"向导多选场次 → 顺序 stage（各出比对表）→ 顺序 commit"。千牛联报计划降为**兜底/补充**（并非放弃，只是不作主链路）。
- 三诉求映射：**追加报多个活动 = D**；**自动查报名时间 = A（档期抓取，仍需——喂给向导的场次列表 + 根治口径错）**；**飞书提醒 = C**。
- **修订分期（D 为重心）**：
  - **P0** D 编排器后端 `batch_stage / batch_commit`（纯组合现有单渠道 stage/commit，零新风险，可单测）——先落。
  - **P1** A WA 抓千牛「活动报名」列表 → 档期日历自动同步（需实地看千牛列表页结构）。
  - **P2** 前端 `ActivityAutoFillTab` 多选场次向导（读 A 的档期 → 顺序推 D）。
  - **P3** C 飞书提醒（每日 08:30）。
- 细节默认值（如无异议按此）：档期同步**每日 1 次**、手工项**不被自动覆盖**；提醒 **08:30**、就绪度**含逐品风险清单**；tier 映射 超级88→big / 618→big618 / 中促→mid / 超级立减→super_reduce。

## 一、背景与痛点
- **档期靠手工录入**：`activity_periods`（system_settings JSON）整表覆盖，人手填 → 「88VIP 被记成 0 点」这类口径错反复出现。
- **报名一次一个档**：super_reduce / single_item_discount / promo_signup(含新增 big88) 各自推，多活动要人肉重复操作。
- **窗口靠人盯**：报名开启/截止无自动提醒，容易错过（88VIP 死线 7-17 20:00 就是靠人记）。

## 二、★关键发现：千牛原生「联报计划」已开通
stage 88VIP 时截图实证——大促报名页顶部：
> 「多场活动自动报名…**开通联报计划，系统将在计划内其他活动开启报名后的次日自动报入**；请提前设置活动期内的店铺相关优惠，**避免价格不符合活动要求报名失败**」——状态 **【已开通】**。

**含义**：平台**已经**能自动把店铺报进后续在计划内的活动（次日自动报入）。所以"一次联报多活动"的**提交**动作平台侧已具备；唯一风险是"价格不符合要求 → 报名失败"。

→ **方案重心**从"ERP 重造多活动推送"转为"**ERP 保证价格就绪 + 档期同步 + 提醒**"，让千牛联报计划去提交，更省事、更不易碎。同时保留**可选**的 ERP 主动多推（WA 驱动）兜底联报计划没覆盖的活动。

## 三、架构：三支柱 +（可选）第四

### A. 档期自动同步（P0 · 最高价值 · 根治口径错）
- **WA 新增 task** `scrape_activity_signup_list`：抓千牛「营销 > 活动报名」列表页 → 返回
  `[{活动名, 报名start, 报名end, 活动start, 活动end, 联报状态, status}]`。
- **ERP**：`web_agent_service.fetch_activity_list()` 包装 + `activity_calendar_service.sync_from_qianniu()`：
  抓到的档期**自动 upsert** 进 `activity_periods`（**千牛 = 档期唯一真源**，取代手工录入）。
  tier 由活动名关键词映射（超级88/88VIP→`big`，618/双11→`big618`，中促→`mid`，超级立减→`super_reduce`）。
- **定时**：每日（或每 2h）自动跑 → 档期日历永远跟千牛一致，不再靠人记。
- **数据模型**：`activity_periods` 每项扩 `{signup_start, signup_end, qn_activity_id, source:'auto'|'manual', last_synced}`；
  手工项（source=manual）保留、不被自动覆盖（允许人工兜底/纠偏）。

### B. 价格就绪 · 联报前置（P0 → P1）
- **目的**：联报计划"次日自动报入"用的是**当前价**，价格不符即失败。ERP 在每个报名窗口**开启前**确保：
  活动价=日常价 已铺（标价对齐 ÷0.75）+ 该档单品立减（mid/big/big618 的 deduct）已挂。
- **复用已有**：`build_super_reduce` / `build_promo_signup_daily(big88)` / `build_single_item_discount` +
  `activity_preflight_service`（预检 15 天线 / 动销 / 整商品完整性）。
- **产出「联报就绪度」报告**：对每个即将到来的活动，列 预检通过 / 风险清单（会失败的品 + 原因），供运营提前处理。

### C. 飞书提醒运营（P1）
- **scheduler 新增 job** `activity_signup_reminder`（每日 08:30）：读 `activity_calendar.status()` + 就绪度报告 →
  对"报名窗口今日开启 / 临近截止"的活动，走 `notify_service.broadcast_text`（飞书）推：
  活动名 / 报名截止 / 预检结果（X 品就绪 Y 品风险）/ 待办清单（如"抬某品一口价到日常价÷0.75"）。
- 运营照单操作，**不依赖 AI 在场**。企微默认静默（briefing_only），飞书为主通道。

### D.（可选）ERP 主动多活动联报（P2）
- 若某活动不在千牛联报计划内 / 需精确控价：前端 `ActivityAutoFillTab` 支持**多选场次** → 每个场次按 tier 选对应
  builder → 顺序 stage（各出比对表）→ 用户一次确认 → 顺序 commit。
- 编排器 `activity_upload_service.batch_stage(list)` / `batch_commit()`：把现有单渠道 stage/commit 串成队列 + 统一比对表。

## 四、前端改动（`ActivityAutoFillTab.tsx`）
- 顶部档期日历改为**千牛同步态**：带 source 标记（auto/manual）+ last_synced + 手动「立即同步」按钮。
- 多选场次区（P2）：勾选即将到来的活动 → 显示每档就绪度 → 一键联报（走 D）。

## 五、分期
| 期 | 内容 | 风险 |
|---|---|---|
| **P0** | A 档期自动同步 + B 就绪度报告（只读） | 零写入风险，先落，直接根治口径错 |
| **P1** | C 飞书提醒 | 低 |
| **P2** | D 主动多推 UI | 中（走既有 stage/commit，可控） |
