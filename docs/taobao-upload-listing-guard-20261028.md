# 淘宝上传前的整款与规格状态检查

用户于 2026-10-28 要求代码执行，不只写规则。检查不改变 ERP 价格、淘宝状态或优惠。

## 执行链

1. `taobao_export_service._fetch_rows` 排除整款下架、状态未知、精确规格下架；同款其他在售规格保留。
2. 活动生成器的 `delisted_sku_service.get_delisted` 动态合并 ERP 下架规格当前主/备用淘宝 SKU。派生集合不写回平台永久排除表，重新上架不会被旧派生记录锁住。
3. `web_agent_service.upload_file` 在启动浏览器前及启动完成后各查一次当前数据库。覆盖商品价格/信息、单品立减、超级立减、活动报名的 stage/commit。
4. Windows Web-Agent 的实际文件挂载前再用 `scripts/check_taobao_upload_listing.py` 只读查询群晖。现有 uploader、atomic workbook_payload 和旧 plan8 表格恢复入口都走此门。上传的是核验过的字节，避免检查后路径被替换。

## 权威与失败行为

- 整款：`Product.listing_status`；在售、上架、出售中可以继续，其他状态拒绝。
- 规格：`product_sheet_sku_status_overrides_v1` 精确 ERP SKU 编码，或产品编码 + 完整规格名称。现有 21 条登记含 7 条尚未建档的规格。
- 平台排除：`delisted_skuids`；主 ID、备用 ID 和后续映射均检查。
- 身份：当前 PricingSkuPromo 精确 item/SKU 映射优先，TaobaoListing 只补当前映射不存在的旧导出对应。不能用旧导出覆盖新 ERP 对应。
- 新品无淘宝 SKU ID 时要求精确 ERP SKU 商家编码；不按名称猜配。商品商家编码与 SKU 商家编码区分。
- 旧上传表重新检查；缺登记、无法联系群晖、未知或冲突身份都不能上传。错误返回具体行与原因。程序不擅自改写混合旧表，应按当前范围重新制表。
- 官方多行表头、说明行及商品 ID 合并单元格按实际结构读取；无合并证据不向下猜填。原文件、隐藏表、XML、价格及文件哈希不变。
- 本地 `data/output/upload-listing-guard` 留存每次实际挂载前的核验回执。不缓存“可上传”决定。

## 边界

本次是商品表格/立减表格/活动表格上传门，不修改订单、发货、评价图片、素材上传、既有活动或价格。人工绕过程序直接操作淘宝不在此程序控制范围。测试使用内存数据库和模拟上传，不向淘宝实际提交。

## 关系审查

关系流程 CLI 对新增服务及本机桥接仍报告未建模；已人工逐项检查：商品/规格状态与映射 → 导出筛选 → ERP 上传入口 → Windows 文件上传 → 原有平台回执。无订单、财务、库存、工厂表、飞书业务写入变化。未将“未建模”解释为无影响，也未伪造关系图指纹。
