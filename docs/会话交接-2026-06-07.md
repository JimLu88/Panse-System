## ⚠️ 关键数据真相（实测确认，避免重新踩坑）

1. **`AlipayFlow.amount` 是带符号的**（负=支出确实存在），不是绝对值。模型注释「正/负=收/支」正确，既有 `sum(-amount)` 判支出是对的。
2. **2% 补贴税已物化在数据里**：订单总表导入的 805 单 `Order.tax == buyer_payable_amount × 0.02`（805/805 精确），且 `shop_received_amount = 买家应付 − 2%税 − platform_fee(软件服务费~0.6%)`（全部 ±1元 取整内）。逐笔对账据此算 **理论应到账 = 应付 − 2%税 − 软件费 = 店铺实收**。
3. **`Order.alipay_flow_no` 对不上库内 `AlipayFlow.transaction_no`**（986 单只 13 单命中，全是爱群号）。那 986 个流水号来自订单总表 AM 列，跟导入的企业号 456 笔不是一套。企业号 `platform_order_no` 是 45… 号段，订单表是 51…/33… 号段 → 企业号那些是更早的订单，还没进 orders 表（用户说的「早一点的订单在支付宝里」）。
4. **企业号流水号前 8 位 = 交易日**（`2026040722…` → `2026-04-07`）。`alipay_import.date_from_flow_no` 导入时兜底，`alipay_backfill_service.backfill_transaction_time` 修历史（已补 722/1276 含全部 456 企业号）。
5. **到账证据覆盖率只 3.5%**（45/1278 单有支付宝/微信流水）。逐笔对账诚实标 `pending`(待补流水)；订单侧金额(应付/实付/实收/2%税)是完整的。覆盖率要靠**补导早期订单 + 更多 billDetail/企业号流水**才上升。
6. **聚合结算只走微信**（billDetail = `order_settlements`）；支付宝支付的订单货款在企业号(9A)。
7. **销售排行榜排除了补差价/邮费/专拍等非产品**（否则一个差价链接 58066 件霸榜）。口径=正式销售不含补单，销售额=买家实付。
8. **支付宝账户清单**：企业号(9A，淘宝结算) / 爱群号(9C，货款转账个人) / 主力号(komo转账/采购/广告) / 佳宝号(理财)。

## 环境坑（重要，针对本地 D:\AI\Panse-System / Git-Bash + Docker）

- **MSYS 路径改写**：Git-Bash 下 `docker compose exec ... /tmp/x.py` 和 `docker run -w /app` 的绝对路径会被改写成 Windows 路径 → 一律前缀 `MSYS_NO_PATHCONV=1`。
- **前端 tsc 验证**：web 容器只有 512MB，`tsc` 会 OOM。用 2GB 临时容器复用镜像 node_modules：
  ```bash
  MSYS_NO_PATHCONV=1 docker run --rm -m 2g -w /app \
    -v D:/AI/Panse-System/frontend:/app -v /app/node_modules \
    panse-system-web npx tsc --noEmit
  ```
- **api 代码是 bind-mount，uvicorn 无 `--reload`** → 改后端路由要 `docker compose restart api`；但新开的 `docker compose exec api python` 进程读的是最新代码（适合跑诊断/单测）。
- **GateGuard 钩子（ECC）** 拦每个文件首次 edit/write，要求给「调用方/无重复/数据I-O/用户原话」4 条事实，给出后重试即放行。
- **PowerShell here-string 会把代码里的中文字面量变成 `????`** → 需要中文字面量的脚本用 Write 工具写文件 + `docker compose cp` 进容器再 exec，别用 stdin 管道。
- 工作区有意不提交的未跟踪文件：`backups/`, `storage/`, `docker-compose.override.yml`, `deploy/windows/build|*.spec`。

4. **工厂未付款虚高**：`FactoryOrder.payment_status` 默认 unpaid 从未回填。
