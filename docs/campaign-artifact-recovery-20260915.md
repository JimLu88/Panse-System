# 2026-09-15：生成产物与连续执行恢复

用户批准修复完成后继续报名，并要求本次核对独立定制商品链接。价格规则、
ERP可售与淘宝上架交集、九斗柜暂缓、成功/未知不重传均未改变。

## 固定程序行为

1. 每个生成动作保存 business input context，包含精确活动/优惠窗口、价格与
   模板来源、SKU范围、修正依据。软件版本不参与业务幂等键。
2. 第一次生成仍使用官方模板和原生成器。文件已经完整存在时，核验bundle、
   原始文件字节、价格/映射版本、优惠复用证据，采用原产物，不重新生成/上传。
3. 旧产物没有context时，仅允许从Authority完整bundle恢复精确、显式范围；
   缺文件、半文件、来源变化均保持原记录并输出具体原因，不删除claims。
4. continuous generate处于interrupted_read时，由Store自动调用固定恢复器，
   保存恢复回执后继续本场后续步骤。signup/discount/repair未知不走这个分支。
5. 维护部署后的旧blocked worker从统一recover-local-artifact接口恢复一次。
   同一个候选版本/动作不反复尝试，不接受浏览器代码或任意脚本路径。
6. 每段与每个Web-Agent job之前核验ERP与Web-Agent代码清单；代码中途改变
   即停止新动作并保留已提交状态。运行版本不替代业务证据或已加载模块验收。
7. continuous_campaign_diagnostics记录步骤、稳定错误代码与耗时，不包含客户
   文本、网址、凭据，不再只输出ValueError。AI不逐job查询、不监工唤醒。

原普塔专用local-generation修复函数只保留兼容入口，转到通用接口；不再直接
修改controller表或再次调用生成器。其他历史恢复证据和入口不批量删除。

## 测试边界

`scripts/tests/test_campaign_artifact_recovery.py`使用隔离SQLite和真实Store、
CampaignTransport、_generate、claim消费、官方终态解析，仅替代外部平台响应。
覆盖生成完成/状态未落库后重启、普通优惠复用、全定制商品不叠加单品优惠、
成功后二次运行无副作用、提交后未知不重传、文件损坏/缺失仍保留claim、输入
变化、平台处理失败集中报告、代码版本中途改变。

真实普塔现有bundle已只读核验：6条SKU，新增优惠0条。不通过模拟结果宣称真实
报名成功；必须由03一次启动固定程序，并取得终态及最终逐SKU导出。

独立定制链接若ERP主档缺失或可售状态不明，必须单独列出，不能悄悄过滤，也
不能仅以名字含“定制”就推断价格规则或擅自修改主档。已有定制分类与价格
完整时，首次保持当前日常价不要求虚构首次原价；降价才检查已固定的20%基线。

## 本次交接原则

真实试运行又暴露两项边界缺口并纳入同一修复：已在线服务不依赖NAS唤醒；
同活动多个保留标签页不再要求人工关页，而在独立程序页录屏后进入固定地址。
原始signup在page绑定前失败时，程序仅使用既有固定恢复器：同时验证canonical
claim尚未消费、绑定前调用位置、没有before/official-batch证据，才允许一次
原动作继续。未知上传绝不走这个分支。

program-owned恢复器现在同时支持常规segments布局和历史execution布局，原
普塔分支也接入同一完整执行器。完成的原signup job只做官方回执归档和本地
checkpoint恢复，再继续最终导出，不再次上传。失败摘要保留明确的内部原因码。

发布前保存代码/安装哈希与测试清单。03仅确认目标并启动一次，程序执行中不
改代码、不反复发恢复指令；最终回执必须区分已报名、正常待生效、失败与未知。
未通过验收的能力（如无损修复半文件、未知平台写入自动判定）不得宣称就绪。
