# 活动报名全量失败复盘与自动化闭环（2026-08-30）

## 结论

这次复盘不是只处理某一张截图。维护侧逐项检查了生产数据库中 76 条活动接口审计、
48 条失败的活动定时任务、15 份核对报告、9 份结构化证据，以及 NAS 自 7 月以来的
活动导出、失败表、截图和报名准备文件。

历史问题的共同根因是：每次事故虽然都有局部修补，但平台写入前没有一条统一、持久、
跨重启的总状态机；同一个平台状态在不同临时入口里还可能被解释成不同含义。因此程序
能修掉当次按钮、分页或导出问题，却不能从机制上证明“同一批数据绝不再提交第二次”。

本次修复把所有已知失败统一收进同一条流水线：

1. ERP 后端生成精确活动身份、商品、SKU、报名价、立减与最终价。
2. 只读刷新官方活动证据和当前商品全 SKU 清单。
3. 所有价格、动销、SKU 完整性和活动身份硬门通过。
4. 数据库为这份不可变报名清单领取唯一一次平台写入权。
5. Web-Agent 只执行这一次上传/提交。
6. 读取平台终态和新鲜逐 SKU 导出；只有两者都成功才算完成。
7. 任一未知结果都停止，不自动重报；只有“尚未领取写入权”的网络/启动故障可自动续跑。

## 全部已知失败类型与现在的处理

| 历史失败 | 原因 | 现在如何避免再犯 |
|---|---|---|
| Web-Agent 离线、8500 拒绝、启动超时 | 主力机按需启动或 Docker/浏览器暂不可用 | 写入前的纯读取故障保留计划状态，下个小时安全重试；没有上传就不会把计划永久卡死 |
| 登录、二维码、验证码 | 平台要求真人交互 | 明确停在人工门并保留现场；绝不绕过，也绝不把它当普通网络故障循环重试 |
| 活动不存在、标题不符、进错商品中心 | 页面复用、重定向或活动身份不完整 | 标题、campaignId、unitedActivityId、signRecordId、档期和力度共同锁定；任何一项不符都在写入前停止 |
| 导出按钮找不到、被快速报名层挡住 | 千牛 DOM、遮罩、标签页发生变化 | Web-Agent 只在精确活动容器内找只读动作；安全关闭/精确只读路由失败就停止，不穿透点击、不猜按钮 |
| 导出轮询超时、直接下载和异步记录混淆 | 平台有两种导出结果形态 | 同时捕获直接下载和异步操作记录，并保存 job、文件名、大小、SHA256 与失败步骤 |
| “加载更多”非唯一、候选分页漏读 | 控件跨容器重名或虚拟列表 | 在候选抽屉和商品列表容器内做语义唯一选择；页数、商品数、SKU 数都进入结构化回执 |
| 最新证据未提交、错误回退旧计划 | 事务未提交或查询没有限定计划 | 证据按 workflow/plan/request 固定保存；本计划没有证据时返回空并硬停，禁止借用旧计划 |
| H/I 价格线为空、候选 SKU 漏取 | 已报商品导出不覆盖未报名候选 | 已报与候选价格证据分开获取；缺官方可见价格的商品安全暂缓，绝不上传探价 |
| 无效商品号 `5/待定/暂无` 被登记 | 输入身份未校验 | 只有纯数字淘宝商品号可进入动销登记和报名范围 |
| 无动销商品仍进入报名 | 旧 R6 仅提示、不排除 | 已确认无动销整品从活动报名表排除；不会靠改价或换 SKU 强行报名 |
| 定制/补差价误杀正常商品 | 用名称关键词猜整品属性 | 只认显式整品排除或“全部 SKU 都是占位”的权威事实；混合正常商品保留真实 SKU，不按名称猜 |
| 正常商品漏掉新增 SKU | ERP 映射旧于淘宝当前商品 | 最终写入前下载官方当前商品表，逐商品要求完整 SKU 集合完全一致；空白合并续行也会正确读取 |
| 报名价/最终价/价格线冲突 | 日常价、官方力度、券后线或目标价格不一致 | 报名价必须等于 ERP 日常价；最终价必须等于中促/大促目标；不降价、不轮换 SKU，冲突整品暂缓 |
| 把 `暂停` 误认成“草稿待发布” | 只看状态文字，忽略文件是“已报商品” | 统一分类为“已经报名但暂停”；旧全局一键发布入口已退役，迁移 0145 修正历史证据 |
| 平台显示成功，逐 SKU 导出却为空 | 平台异步落库或解析字段漂移 | 提交终态不再单独算成功；必须有新鲜官方导出且每个真实 SKU 活动价精确一致 |
| 已经上传后任务超时/重启再跑 | 没有跨进程一次性写入锁 | 数据库在上传前先领取不可撤销写入权；成功、失败、未知均禁止自动重报 |
| 自动发现的计划没有 workflow_key | 重启后缺少稳定活动身份 | 新计划用双平台 ID 与精确开始时间生成稳定 workflow_key；旧计划用不可变 plan id 兼容保护 |
| 通知说“成功”但平台/导出未证明 | 把程序退出、平台终态、最终核验混在一起 | 触发、上传、平台终态、逐 SKU 核验、通知分别记录；只有终态和新鲜导出同时通过才完成 |

## 自动化能做到什么

- 正常情况下，从活动发现、ERP 价格和动销计算、证据刷新、预检、报名文件生成、一次上传、
  平台终态读取到逐 SKU 核验都可自动完成。
- 淘宝临时断线或主力机按需启动较慢，只要尚未上传，程序会在后续定时窗口安全续跑。
- 淘宝页面或政策出现从未见过的变化，程序会在平台写入前停止并留下完整结构化日志，不会
  通过盲点、降价、换 SKU 或重复提交来“硬做完”。

## 仍然必须由用户处理的情况

只有以下情况需要人工：淘宝要求扫码/验证码/重新登录；价格原则发生冲突需要决定是否承担
损失；活动撤回、暂停、移出、改价或付款等高影响动作需要新的精确授权。除此之外，不应再
要求用户逐页抄 ERP 数据、手工判断按钮、手工拼报名表或反复提醒程序继续。

“完全自动化”在这里的可验证含义是：所有已知问题都有自动处理或写入前硬停；平台未知变化
不会造成错报、重报或错价。任何程序都不能诚实保证淘宝以后永远不改页面和规则，但新问题
只能变成有日志、无平台误写的安全停止，不能重演这次的失控链条。
