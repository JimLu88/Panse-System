# 采购系统：群晖 ERP 与 Windows 采购机联机方案

## 目标与边界

采购功能是畔色 ERP 的增量模块，不替换原有配件采购、入库、大宗材料对账、
订单、财务或供应商功能。

- 群晖：继续只运行 PostgreSQL、ERP API、Web 和备份容器。
- Windows 采购机：运行独立采购执行器，运行数据位于
  `C:\Users\Jane\Desktop\AI`，连接独立采购 Chrome 配置及平台消息窗口。
- ERP 只下发已由采购人员明确确认的询价/追问任务，并接收发送结果、商家回复和报价。
- 平台账号密码、Cookie、验证码和支付信息不进入 ERP，也不写入采购执行器配置。
- 本阶段不自动下单、不自动付款。询价可以自动化，正式采购仍需要人工确认。

## 与现有 ERP 的隔离

1. 数据库迁移 `0134`—`0136` 创建采购表，`0138` 只增量扩展采购任务和询价记录；
   不改订单、财务等业务逻辑。
2. 新界面只追加在“配件采购 → 智能询价”页签；原菜单名称、默认页和原页签顺序保持不变。
3. Windows 采购机使用独立 `PROCUREMENT_AGENT_TOKEN`。
4. 该令牌只允许访问 `/api/procurement/agent/*`，不能访问订单、财务或其他 ERP API。
5. 每个商家任务有租约和幂等回执，避免两台电脑重复发送。
6. 任务级话术允许原样人工确认，但每一家商家的首轮消息和每轮追问仍必须逐条最终确认；
   未确认内容不会进入发送队列。

## 完整状态流

1. ERP 创建采购需求，并生成一组可编辑的多关键词搜索计划和 A/B 话术建议。
2. 采购人员检查并明确确认任务级话术；准确时可以原样确认，不强迫做无意义改字。
3. Windows 执行器领取 `discovery_ready` 槽位，在选定渠道搜索候选，不向商家发消息。
4. 候选商家写回现有 `procurement_inquiries`：记录店铺、商品链接、搜索词、评分和安全快照；
   同任务按店铺身份去重，避免重复联系。
5. 采购人员查看候选，并对每一家最终消息逐条审核。只有审核后的 `action_key` 可领取发送。
6. 执行器每轮先收取回复，再搜索候选，最后领取待发消息，避免收到回复后误发催问。
7. 回复按价格、运费、交期、规格、材质、起订量等字段整理；缺失字段生成下一轮建议，
   仍需人工确认且受最大追问轮数限制。
8. 验证码、风控、登录失效、要求加微信、无法理解的回复立即转人工。
9. ERP 可记录入围、选定、淘汰，并可由人工关联既有 `PartPurchase`；关联不触发下单或付款。
10. 日报分别统计新候选、待审核、已询价、有回复、转人工、已选定和已关联实际采购记录。

## 渠道与执行端

| 渠道 | 执行端能力 | 首期工作 |
| --- | --- | --- |
| 淘宝 | `taobao_desktop` / `taobao_chrome` | 询价、最多 N 轮追问、回复回收 |
| 1688 | `1688_chrome` | 限速询价、报价回收、异常转人工 |
| 拼多多 | `pinduoduo_chrome` | 候选搜索、询价、报价回收、异常转人工 |
| 小红书 | `xiaohongshu_chrome` | 私信询问、长期轮询回复、回复后继续追问 |

渠道每日上限由每个 ERP 采购任务单独设置。执行器不提供绕过平台限制、验证码或账号风控的功能。

## 上线顺序

1. 在 PC 完成专项测试和前端构建。
2. 确认群晖四个生产容器健康、生产提交与当前 Alembic head，并确认最近备份有效。
3. 提交并推送同一份 `main`；生产只使用 `scripts/deploy_release_nas.sh`。
4. 发布脚本给旧 API/Web 镜像打回滚标签，再部署同一 Git 提交的 API 与 Web。
5. 迁移到 `0138` 后验证：
   - 既有 `/api/health`、`/api/ready` 和关键业务路由仍正常；
   - API/Web commit 完全一致；
   - `procurement_tasks`、`procurement_inquiries`、`procurement_messages`、
     `procurement_agent_states` 存在；
   - 原“配件采购”默认仍进入精选视图；
   - “智能询价”页可创建任务，但未配置 PC 令牌时执行器接口保持关闭。
6. 单独生成采购执行器强令牌，分别写入群晖 `.env` 和 Windows 本机环境变量。
   不通过聊天、Git 或配置文件传递令牌。
7. PC 先以 `dry_run` 连续跑，确认四渠道、搜索词、商家、话术、每日上限均正确。
8. 再切到 `review`：每次发送仍在 PC 显示最终内容并由人工确认。
9. 经过小批量验证后才评估 `live`；下单和付款始终不进入 `live`。

## 浏览器与人工条件

- Codex 内置浏览器适合由当前任务进行有人监督的供应商探索，但它是独立会话，
  不能作为 Windows 常驻执行器的后台控制接口。
- 常驻询价和回复回收使用独立采购 Chrome 配置；不读取个人 Chrome 配置，也不把
  Cookie、账号密码或验证码写入 ERP、Git、配置或日志。
- 首次进入淘宝、1688、拼多多等平台时需要采购人员本人登录；验证码和风控必须本人处理。
- “语言风格实验室”尚未发现稳定接口。在获得明确程序路径或 URL 前，执行器只使用 ERP
  内可审计的话术；不会猜测或复制未确认的外部风格配置。
- 商家要求手机号/微信沟通时只记录转人工，不自动加好友或代替采购人员跨平台沟通。

## 停机与回滚

- PC 执行器可随时停止，不影响 ERP 其他模块；未完成租约到期后会自动释放。
- 发现验证码、账号异常、加微信或内容不一致时立即转人工，不继续重试。
- API/Web 发布异常时使用本次发布前生成的成对回滚镜像。
- 数据库迁移采用向前迁移；未经确认不执行 Alembic downgrade。
- 任何采购异常都不能触发删除、覆盖或回滚非采购业务数据。
