# 分段设置优惠时间（2026-09-11 用户已确认）

用户直接答复：“是的，就是分段设置时间”。维护只落程序，不提交报名。

## 固定口径

- 超级立减的长期平台有效期只表示该活动可用到什么时候，不是单品立减时间。
- 日常空档使用中促 M；88VIP 12% 与大促 15% 的实际售卖窗口使用大促 B。
- 时间按北京时间精确到秒，闭区间。前一段结束时间=后一段开始时间−1秒。
- 同一商品不叠加单品立减。已有成功/未知优惠不得因新计划自动取消、裁短或重传。
- 不猜未来活动日期。不把“尚未发现下一场活动”解释成可以设置到2028年。
  输入必须带明确覆盖期和本轮发现的完整已知活动。若覆盖期截断一场已知大促，
  本地计算要求调用方延展覆盖期到完整官方窗口，而不是提交一半的大促优惠。
- 已知大促相互重叠时不能自行猜优先级，即使两场目标都是B，12%和15%的立减额也不同。
  这类冲突返回具体日期供统一处理，不增加平台预检、不自动撤回活动。
- 日常价、同一ERP价格版本、固定原始定制价格20%底线、失败范围和成功防重放不变。

例如，已核验的秋季窗口为9月16日20:00:00至9月27日23:59:59：前段M截止
9月16日19:59:59；大促段使用B；后段M从9月28日00:00:00开始，结束取明确覆盖期。
这是时间计算说明，不是已设置或已报名回执。

## 程序入口与防误用

独立合同 `campaign-segmented-time-20260911.json`，规范化SHA256：
`65f805171600b71cc3e7d23dcab54442cfda25740330a66fc8508ab3acf3445d`。
连续报名旧合同500d344d…和更早的7ff08aaa…均不改写，旧批次按原含义核验。

1. `campaign_segmented_time.build_plan(request)` 接收已有发现结果、店铺、精确三段活动ID、
   来源证据、价格版本和显式覆盖期，计算段与segment_id。只做本地计算，不查浏览器。
2. `campaign_generate_current_files.py --time-request <原始计划输入.json>
   --time-segment <segment_id> --continuous-rule-sha <原连续规则SHA> …`
   仍生成同一价格版本的两份官方格式文件。`--start/--end`是选定的**优惠时段**。
   生成前要求活动、M/B、力度、价格版本和时段完全吻合；不修改固定模板。
3. bundle保存完整time_binding、原始输入文件路径/指纹、plan_id及精确段。
   受控提交前在原生成校验内复算；不能改JSON后沿用旧文件、偷换长有效期或换价格版本。
4. `phase_window`：discount凭证/回执使用优惠时段；signup凭证/回执使用官方活动有效期。
   旧无time_binding的凭证保持原语义；不会迁移旧unknown到新通道。
5. 连续控制器显式接收time_binding，所有步骤带同一绑定；生成器不能丢字段退回旧逻辑。
   优惠读回必须匹配分段时段，不接受“平台有效到2028年”作为优惠时间正确。
   已经报成功的日常商品仍处理新优惠段，但不重传报名表；新商品仅上传其自身范围。

原始计划输入应另存新文件，不覆盖已绑定旧文件；新增活动改变分段时生成新计划，
原成功/未知优惠冲突由持久Authority拦住，不能用新计划ID规避。
