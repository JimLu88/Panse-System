## 1. 项目目标

物流费用账单原先只能看到日期、承运商、运单号、收货人、目的地、订单匹配、重量和运费，无法直接判断“这笔物流费对应什么产品”，也不能系统比较：

- 某个产品在不同省市的实际运费；
- 不同省份、重量、体积区间的运费；
- 某个产品不同时期的运费波动；
- 不同承运商的实际价格；
- 可能异常偏高的单票运费。

本项目在不修改历史账单、不新增数据库迁移的前提下，增加订单产品关联、统计接口和前端分析页。

## 2. 用户可见功能

入口：ERP → 物流 → 物流费账单。

页面顶部现在有两个 Tab：

1. **账单明细**
   - 新增“产品名称 / SKU”列；
   - 显示产品编码或 SKU 编码；
   - 显示计费重量、实际重量、体积和包裹件数；
   - 多品合箱标记为“多品合箱·不进单品均价”；
   - 同款多件标记为“同款 N 件·不进单件均价”。
2. **物流统计分析**
   - 产品、省份、承运商、日期范围筛选，所有表格和图表联动；
   - 省市运费统计；
   - 省份 × 计费重量档 × 体积档统计；
   - 产品总体运费统计；
   - 产品在不同省市的运费；
   - 产品月度平均运费趋势；
   - 承运商价格统计；
   - 异常高价账单提示；
   - 产品关联、计费重量、实际重量和体积覆盖率。

## 3. 架构与数据流

```text
物流账单导入
  └─ logistics_bills（日期、承运商、运单、订单号、目的地、重量、体积、运费）
       │
       ├─ 订单号 → orders（客户与主订单兜底信息）
       └─ 订单号 → order_details(source=import)（权威商品明细）
                         │
                         ├─ 过滤服务/补差/退款行
                         ├─ 合并相同产品与 SKU 数量
                         └─ 判断单品单件 / 同款多件 / 多品合箱
                                      │
                  logistics_analytics_service.py
                     ├─ 产品上下文批量关联
                     ├─ 省市解析与重量/体积分档
                     ├─ 聚合、趋势和异常检测
                     └─ 只读 JSON 统计接口
                                      │
                  LogisticsAnalyticsPanel.tsx
                     ├─ 筛选与概览卡
                     ├─ ECharts 图表
                     └─ Ant Design 明细表
```

### 后端

- `backend/app/services/logistics_analytics_service.py`
  - `product_context_by_order()`：批量取得订单商品，避免列表逐行查询；
  - `parse_region()`：从目的地提取省份和城市；
  - `_weight_band()` / `_volume_band()`：生成重量和体积分档；
  - `_aggregate()`：统一生成票数、总额、均值、中位数、范围及覆盖样本；
  - `build_analytics()`：生成全部统计结果。
- `backend/app/api/finance.py`
  - 扩展 `LogisticsBillOut` 产品及重量体积字段；
  - `_enrich_logistics_bills()` 将产品上下文合并到账单列表；
  - `GET /api/finance/logistics-bills/analytics` 提供只读统计。

### 前端

- `frontend/src/pages/LogisticsBillsPage.tsx`
  - 增加产品、SKU、实际重量、体积、件数列；
  - 增加“账单明细 / 物流统计分析”Tab。
- `frontend/src/components/LogisticsAnalyticsPanel.tsx`
  - 提供筛选、概览、区域、产品、趋势、承运商和异常分析。

### 数据库

- 本项目**没有数据库迁移**；
- 不回写物流账单、订单、产品或价格字段；
- 产品名称是请求时从订单数据实时关联，不是复制保存到物流账单表。

## 4. 已确定且不得随意改变的统计口径

### 4.1 产品来源优先级

1. 优先使用 `order_details` 中 `source="import"` 的商品明细；
2. 过滤安装、送货、入户、上门、运费、补差和差价类非实体行；
3. 过滤取消、售后或明确退款的商品行；
4. 如果订单存在导入明细，即使明细全部退款/被过滤，也**不得**回退主订单重新算入；
5. 只有完全不存在导入明细时，才使用 `orders` 主表商品作为兼容兜底。

### 4.2 单品运费口径

- 一票物流费属于整票发运；
- 只有“一个唯一实体商品规格，且数量等于 1”的账单进入产品均价；
- 多品合箱不把整票运费重复分配给每个产品；
- 同款多件不进入单件均价；
- 未来如果需要多品或多件分摊，必须先确定可审计的分摊规则或取得实际分项费用，不可默认为平均分。

### 4.3 重量与体积

- 重量分档使用物流公司的**计费重量** `weight_kg`；
- 实际重量 `actual_weight_kg` 单独展示；
- 体积使用 `volume_m3`；
- 页面显示各字段覆盖率，缺数据不推算为 0。

### 4.4 样本与异常

- 样本少于 3 票统一显示“仅参考”；
- 异常规则只在“同产品、同规格、同省份”至少 3 票时启用；
- 单票同时满足：高于该组中位数 50%，并且绝对高出至少 30 元，才进入异常列表；
- 异常只提示人工核查，不自动判定账单错误，也不写回任何数据。

### 4.5 时间趋势

- 当前按月统计产品平均运费；
- “较上个有数据月份”是与该产品上一个存在样本的月份比较，不保证两个自然月连续；
- 趋势是原始实际均价，尚未控制重量、体积、目的地和承运商结构变化，不能直接解释为物流公司单价涨跌。

## 7. 未完成事项与已知数据问题

按优先级排列：

1. **78 票缺产品关联**
   - 主要来自账单未配订单、历史订单缺失或订单产品明细不足；
   - 应先补订单匹配和历史明细，再观察产品分析覆盖率。
2. **主订单兜底仍可能带入非实体链接**
   - 当前候选产品出现“差价邮费补拍专链”；
   - 原因是非实体过滤目前只作用于 `OrderDetail`，主订单兜底尚未套同一规则；
   - 修复时必须加测试，避免影响真实定制链接。
3. **产品名称未规范化**
   - 当前使用淘宝完整商品标题，较长；
   - 有一条商品名出现同一标题重复拼接多次；
   - 后续宜关联 ERP 标准产品名称/产品编码，并保留原始标题供追溯。
4. **历史关联疑似异常**
   - 样块商品出现数百公斤、数立方米和高额运费样本，可能是错误配单、合箱或历史商品信息不完整；
   - 不应直接据此判断样块物流价格，需要逐票核查。
5. **自治区名称只做简化归一**
   - 当前可能显示“广西自治区”“新疆自治区”，未展开为完整行政区名称；
   - 不影响聚合，但展示可进一步规范。
6. **趋势未做结构归一化**
   - 月度均价会受目的地、重量、体积、承运商和样本构成变化影响；
   - 若要做物流商涨价判断，应新增“同产品 + 同省份 + 同重量/体积档”的可比趋势。
7. **统计暂不支持导出**
   - 当前只有页面查看和筛选；
   - 后续可增加“导出当前筛选统计”，但必须保留统计口径和生成时间。
8. **大数据量性能尚未压测**
   - 当前 183 票运行正常；
   - 统计接口会加载筛选范围内全部逐单账单，数据增长到数万票后应评估索引、缓存或数据库聚合。

## 8. 注意事项

- 不要把“订单已匹配”理解为“产品一定可靠”；客户匹配、商品明细和物流分票是三个不同层次。
- 不要给多品合箱或同款多件自动平均分配运费。
- 不要把缺失重量/体积当成 0。
- 不要仅看平均值；中位数、样本量和范围必须一起看。
- 不要把“较上个有数据月份”误写成严格自然月环比。
- 生产 OpenAPI 文档当前关闭，不能用 `/api/openapi.json` 的 404 判断业务路由不存在；应直接请求目标接口并核对状态与响应结构。
- 页面部署后如仍显示旧版，先检查 `/api/version` 与 `/build-version.json`，再使用 `Ctrl + F5`；不要先归因于浏览器缓存。
- 本仓库可能同时存在另一台电脑/另一会话的未提交工作。提交本项目时必须显式列文件，禁止 `git add -A`、强制重置或覆盖其他改动。
