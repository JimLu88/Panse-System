# 群晖 (Synology) 部署清单

> 2026-06-11 整理。迁移时按顺序逐项打勾。前置条件: 群晖已装 Container Manager (Docker)。

## 一、迁移前必做 (在现机器上)

- [ ] **前端生产构建**: 现在 web 容器跑的是 vite dev 模式 (体积大、启动慢)。
      部署前把 frontend Dockerfile 改成两段构建: `npm run build` → nginx 托管 dist。
      ⚠️ 用户计划先做整体 UI 改版, 改版完成后再做此项 (两件事一起)。
- [ ] 跑一次全量备份并校验能恢复: `./backups` 里最新 `panse-*.sql.gz` 拷出来,
      在群晖上 `gunzip -c xx.sql.gz | psql` 演练一遍。
- [ ] 导出 `.env` / docker-compose 里的所有密钥 (POSTGRES_PASSWORD、AI key、飞书 app secret、
      system_settings 里的 webhook) — 群晖上重新配置, 不要把密钥提交进镜像。

## 二、文件与卷 (路径对照)

| 用途 | 现路径 (Windows) | 群晖路径 (建议) |
|---|---|---|
| 代码 | `D:\Panse-System` | `/volume1/docker/panse-system` |
| 数据库卷 | docker volume `pg_data` | 同名 volume (用 pg_dump 迁数据, 不搬卷文件) |
| 上传/归档/缩略图 | `./storage` | `/volume1/docker/panse-system/storage` |
| 备份 | `./backups` | `/volume1/docker/panse-system/backups` (再配 Hyper Backup 异地) |
| **产品图库** | `D:/畔色 产品图库` | `/volume1/photo/畔色产品图库` — **只改 docker-compose 这一行挂载, 代码零改动** (GALLERY_ROOT 已抽环境变量) |

## 三、安全三件套 (审核项 18/19/20, 上外网前必做)

- [ ] **18 CORS + HTTPS**: `CORS_ORIGINS` 改成真实域名 (如 `https://erp.xxx.synology.me`);
      群晖反向代理终止 TLS (控制面板→登录门户→高级→反向代理), 强制 HTTPS。
- [ ] **19 数据库端口**: docker-compose 删掉 db 服务的 `ports: 5432:5432` 映射
      (容器网络内部互通即可)。⚠️ 确认没有外部工具直连数据库后再删。
- [ ] **20 图库/图片接口鉴权**: 当前所有图片 GET 无登录校验 (内网无所谓)。
      上外网后方案: 图片 URL 加短期签名 token (后端发 URL 时附 `?sig=`),
      或最低限度只把 web 端口发布、API 仅供反代内部转发。

## 四、群晖上的发布方式

- [ ] 反向代理: `https://erp.你的域名` → `web:5173` (生产构建后是 nginx:80);
      `/api` → `api:8000`。或者简单点: 只发布 web, web 容器里 nginx 反代 /api。
- [ ] 外网入口三选一: ① QuickConnect (最简单, 但慢) ② DDNS + 端口转发 (快, 配 HTTPS)
      ③ Tailscale (不暴露公网, 团队内用最安全)。
- [ ] 防火墙: 群晖控制面板只放行 443 (用 Tailscale 的话什么都不用放)。

## 五、容器与调度

- [ ] Container Manager 里用同一份 docker-compose (db/api/web/backup 四个服务)。
- [ ] 资源限制按群晖内存调整 (api 现在 limit 3g, 弱机型降到 2g)。
- [ ] 首次启动自动跑 alembic 迁移 (compose command 已带), 确认 `alembic upgrade head` 到 0077+。
- [ ] 调度任务随 api 进程自动启动, 无需额外配置 (备份/下单图/对账快照/通知重试/缩略图清理)。

## 六、迁移日演练顺序

1. 群晖拉起 db → 恢复最新备份 → 拉起 api (跑迁移) → 拉起 web。
2. 核对: 登录 → 数据大盘数字和老机器一致 → 图库能打开 → 飞书测试通知能收到。
3. 老机器停止写入 (停 api), 终备份 → 群晖再恢复一次 → 切 DNS/入口。
4. 老机器保留只读两周再下线。

## 七、性能预期 (你问过的)

- 数据按"年"分库**不需要**: 已加复合索引 (orders 日期+状态/产品编码, 流水 账户+时间/核销类型,
  采购 日期), PostgreSQL 撑到几百万行没问题; 财务本来按年查, 查询都带日期范围, 索引后只扫当年数据。
  真到千万级再考虑表分区 (PostgreSQL 原生支持, 也不用分库)。
- 外网图片: 缩略图 WebP (原图 8% 体积) + 浏览器 24h 缓存, 群晖上行 30Mbps 也够流畅。
- API JSON 已开 gzip (体积 -80%)。

## 附: Panse-Web-Agent (自动取数) 跨机对接 (2026-06-12 并入)

Web-Agent 依赖真实 Chrome + Windows DPAPI 加密, **永远留在 Windows 机**, 不随 ERP 上群晖。

迁移群晖时只改两处 (docker-compose.yml 的 api 服务):
1. `WEB_AGENT_URL`: `http://host.docker.internal:8500` → `http://<Windows机局域网IP>:8500`
2. 卷 `D:/Panse-Web-Agent/data/output:/app/agent_output:ro` → 改为 SMB/NFS 共享该目录后挂载
   (Windows 侧把 `D:\Panse-Web-Agent\data\output` 共享出来, 群晖挂载为只读)

Windows 机要求:
- Web-Agent 用 `run.ps1` 启动 (已默认绑 0.0.0.0, API 全程 Bearer token; **路由器不要把 8500 端口映射到公网**)
- 建议注册 Windows 计划任务开机自启: 程序 `powershell.exe`, 参数 `-WindowStyle Hidden -File D:\Panse-Web-Agent\run.ps1`
- token 已写入 ERP 系统设置 (web_agent_token); Agent 重装后在「工具→自动取数→更新间隔设置」里重新粘贴

ERP 侧调度: scheduler `daily_0630_web_agent` 每天 06:30 按更新间隔(订单1天/余额流水3天, 设置可改)编排取数+导入+飞书日报。

## 附2: Web-Agent 扫码/卡点回调 → 飞书 (2026-06-12)

渠道分流 (用户拍板): **所有事件/日报 → 企业微信** (notify_provider=wechat_work);
**飞书只发 文件(入站OCR) / 发货密码(入站) / 二维码(出站)**。

Web-Agent 检测到"需扫码"卡点时, 截取二维码 PNG, 调 ERP:
`POST {ERP}/api/web-agent/notify`  body: `{"kind":"qr","text":"支付宝流水需扫码","image_b64":"<base64 PNG>"}`
ERP 会: ①把二维码图发到飞书会话(供手机扫) ②给企业微信发"需扫码"提醒。
- 外发目标会话 = 用户最近一次给飞书机器人发消息的会话(自动记住, 无需手填 chat_id)。
- kind 取值: qr/scan_wait(扫码图) | file(文件预览) | event(纯事件→只进企业微信)。

发货报表口令: 淘宝把口令经微信强提醒发用户 → 用户**转发「发货密码 xxx」给飞书机器人**
→ ERP 存 60 分钟有效口令 → 下次 ingest 自动 msoffcrypto 解密导入。
